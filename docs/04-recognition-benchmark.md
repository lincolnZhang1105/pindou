# 04 拼豆图纸识别准确率 Benchmark 设计

> 版本：v0.2（2026-10-27，根据一致性审查结果修订）
> 目的：在投入开发前先回答一个问题：**我们的端侧识别，能不能在小红书上的真实图纸里明显胜过当前最强的竞品？尤其是大图和糊图。** 胜不过就不入场。

---

## 0. Go / No-Go 判定

### 0.1 指标与门槛（建议值，可调）

| # | 指标 | 数据集 | 门槛 | 性质 |
|---|---|---|---|---|
| 1 | 和最强竞品比格子错误率 | Hard 集里所有参与 Tier B 的图纸（在同一批图上配对比较） | 我方每千颗错误数 **≤ 竞品的 50%**，并且**配对 bootstrap 求出的差值 95% 置信区间下界 > 0**（也就是显著优于竞品） | **go 必要条件** |
| 2 | 每千颗错误数（微平均） | Clean 集 | **≤ 1.0**（相当于格子准确率 ≥ 99.9%） | **go 必要条件** |
| 3 | 不确定标记召回率 | 全部 test 图纸 | 被标为「不确定」的格子 **≤ 总豆数的 2%，且每张图 ≤ 30 格**的前提下，错误格子里 **≥ 80%** 被标了出来 | MVP 上线门槛 |
| 4 | 网格尺寸正确率 | 全部 test 图纸 | ≥ 98% | **go 必要条件** |
| 5 | 端侧耗时 | 104×104 图纸，中端机（Android：骁龙 7 系；iOS：iPhone 12） | ≤ 3 s | MVP 上线门槛（在任务 T0.14 实测，阶段 0 只记录结果） |
| 6 | 图例解析完全正确率 | 带图例的 test 图纸 | ≥ 95% | MVP 上线门槛 |

- **go 的条件**：在冻结的 test 集上，第 1、2、4 条同时达标。
- **第 3、5、6 条**不影响 go 的结论，但必须在 MVP 上线前达标。
- **no-go**：先停下来，由产品负责人复盘。备选方向包括：只做中小尺寸图纸；或者不靠识别取胜，改走「跟拼 + 库存 + 智能板」路线。

### 0.2 定义

- **最强竞品**：Tier A 评测中，用量清单误差最小的那个竞品。如果拼豆大王在测试名单里，通常就是它。
- **Hard 集**：满足以下任一条件的图纸：
  - 尺寸档为 L 或 XL；
  - 带 `watermark` 标签；
  - 带 `blurry` 标签：最小格边长 < 8 px，或者图纸区域的拉普拉斯方差低于阈值 θ（θ 在 dev 集上标定后写进 `bench/eval/config.yaml`，之后冻结）；
  - 类型是 T4（分页图）。
- **Clean 集**：test 集里除 Hard 集以外的图纸。
- **T6（拍照）和 T7（多图合集）**：不计入第 1、2、4 条，单独报告。拍照导入在首发版本里标注为「实验功能」，见 02 的 B7。
- **失败的图纸**：网格尺寸错了，或者处理失败，这张图在零错误率里记为「否」，所有格子都按错误计算（竞品同样处理）。

## 1. 识别任务的输入

### 1.1 实测观察（2026-10-27，样本见 `data/samples/`）

- 小红书 Web 端下发的图片是**有损 WebP，宽度 1000–1080 px**。实测尺寸有 1040×1472、1080×1241、1080×1440，文件 120–220 KB。
- 58×53 格的图纸铺在 1080 px 宽度里，**每格约 17 px，格内色号文字约 6 px 高**，已经接近 OCR 能读的极限。
  - 按这个比例推算：104 格的图每格约 10 px，208 格的图每格约 5 px。**色号文字基本读不出来，只能靠颜色判断。** 这正好解释了用户吐槽最多的「大图识别不准、越往上越对不齐」。
  - **待实测**：用户在小红书 App 里「保存图片」时，拿到的分辨率是否高于 Web 端。这是任务 T0.3 的子项，结果决定大图识别能拿到的输入上限。
- 图纸里可以利用的结构信息：
  - 四周的行列坐标；
  - 每 5 格一条的粗线；
  - 底部的色卡图例（色块 + 色号 + 颗数，比如 `G3 x534`）。图例颗数的总和就是总豆数，样例里是 1885，可以当作校验和；
  - 格内文字是黑色还是白色，取决于底色的亮度。
- 干扰项：
  - 平铺的半透明水印；
  - **白色豆子和空格的颜色完全一样**，只能靠格内有没有文字来区分（样例里 H2 白豆有 264 颗）。

### 1.2 输入类型

| 代号 | 类型 | 说明 |
|---|---|---|
| T1 | 带色号的数字图纸 | 最常见：格内有色号，带图例和坐标 |
| T2 | 纯色块网格图纸 | 有网格线，格内没有色号，可能带图例 |
| T3 | 像素画 | 没有网格也没有图例，需要估计像素尺寸 |
| T4 | 分页大图 | 九宫格或按板子分页，多张图合成一张图纸 |
| T5 | 截图 / 多次压缩 | 带 App 界面、状态栏 |
| T6 | 拍照 | 打印件或屏幕翻拍：有透视变形、摩尔纹、光照不均 |
| T7 | 多图合集 / 封面拼图 | 一张图里有多个独立图案（比如 `data/samples/0_0.png`、`3_1.png`）。**需要用户框选出其中一个**，不进入自动识别的统计 |

## 2. 样本收集

### 2.1 真实样本

**采集方式：人工采集，不用脚本批量抓取。**
- 在小红书或抖音 App 里，人工「保存图片」到手机，再导出到电脑。
- 这样做一是规避 06 第 9 节说的抓取风险，二是让样本和真实用户的输入路径一致。
- `bench/collect` 只负责生成 manifest：记录 note_id、作者、URL、保存时间、sha256，以及 `source_path=app_save | own_export | photo`。

**来源：**
1. 小红书画师发布的图纸（用「拼豆图纸 + IP 名」等关键词，热度和时间混合抽样）；
2. 抖音上的图纸；
3. 「识别错了」「避雷」这类求助帖里的原图（天然的 Hard 样本）；
4. 自己用主流 App（我嘞个豆、拼豆大王、豆画、画像素）导出的图纸，**真值已知**；
5. 自己打印图纸后拍照、对着屏幕翻拍。

**首轮规模：120 张**（不含 T7），按 dev : test = 1 : 2 分层抽样，即 dev 40 张、test 80 张。

| 尺寸档 | 边长（格） | 占比 |
|---|---|---|
| S | ≤ 40 | 20% |
| M | 41–80 | 30% |
| L | 81–130 | 30% |
| XL | > 130，或分页图 | 20% |

**覆盖要求（按 120 张整体统计，不是每个尺寸档都要满足）：**
- 类型：T1 ≥ 50%；T2、T3、T5、T6 各 ≥ 5 张；T4（计入 XL 档）≥ 5 套；**test 集里每种类型至少 3 张**。
- 水印：有水印、无水印都要覆盖；Hard 集在 test 集里应该占到 ≥ 40 张。
- 品牌：MARD 221/291 为主，COCO、漫漫、盼盼、咪小窝各 ≥ 3 张。
- 难点标签：`similar_colors`（白、米白、浅灰）、`single_pixel_detail`（眼睛、高光）、`gradient_skin`（渐变肤色）、`white_vs_empty`、`watermark`、`blurry`。

**第二轮（go 之后的任务 T3.9）：** 扩充到 300 张，用来分辨更小的差距，也作为长期的回归测试集。

**版权：** 只用于内部评测，不对外分发，不进公开仓库。要用于宣传，必须先拿到画师的书面授权。

### 2.2 真值标注

**流程：**
1. 生成初稿：用标注工具的「按图例颜色自动填充」，或导入自研引擎（beadcore v0 起）的预测结果。原计划用 Pindo，但核实后发现它只能识别**不带色号**的图纸，而且是纯浏览器应用（见 4.1），不适合给 T1 图纸出初稿。
2. 在标注工具里叠加原图，逐格修正。
3. **图例校验**：每个色号的格数必须等于图例里的颗数，对不上就打回重标。
4. XL 档和分页图要第二个人复核。

**格式（JSON；色号统一用字符串，不用索引）：**

```json
{
  "image_id": "xhs_6aa72c3e_0",
  "source": {"platform": "xhs", "note_id": "...", "author": "...", "saved_at": "...", "source_path": "app_save"},
  "type": "T1",
  "size_bucket": "M",
  "palette_hint": "MARD-221",
  "images": [{"file": "xhs_6aa72c3e_0.png", "sha256": "..."}],
  "grid": {"cols": 58, "rows": 53},
  "pages": [
    {"image_index": 0, "bbox": [x0, y0, x1, y1], "x_lines": [], "y_lines": [],
     "col_offset": 0, "row_offset": 0, "cols": 58, "rows": 53}
  ],
  "legend": [{"code": "G3", "count": 534}],
  "cells": [["H7", null, "G3"]],
  "tags": ["watermark", "white_vs_empty"]
}
```

- `cells` 里的 `null` 表示空格；色号写成 `palette_id:code` 时，表示混用了其他品牌的色号，比如 `ZG:ZG1`。
- 单张图纸的 `pages` 只有 1 项。分页图有多项，每一页记录它在整张图纸里的列偏移和行偏移。

**工作量估计**（有标注工具时）：
- S 和 M 档每张 5–10 分钟，L 档 20–30 分钟，XL 档 60 分钟以上；
- **首轮合计约 41–52 人时，另加 XL 档的复核**；
- 标注由产品负责人或外包完成，见 07 里的「负责人」列。

### 2.3 合成样本

**用途：** 训练模型和日常回归测试。**不能替代真实的 test 集**，报告里要单列。

**生成方式：**
1. **底图**：开放授权的像素画，或者自己从照片生成的图纸。**每个底图来源都要登记在 05 第 7 节的训练数据登记表里**，因为它们会影响打包进 App 的模型权重。
2. **渲染**：模仿主流 App 的导出样式，包括字体、格内文字颜色规则、网格线颜色、粗线间隔（5 或 10 格）、坐标样式、图例布局。
3. **退化**：
   - 缩放到 1080 px 宽；
   - WebP 或 JPEG 压缩，质量 60–90；
   - 叠加平铺水印；
   - 套一层截图边框；
   - 九宫格或分板切分；
   - 透视变形、摩尔纹、模糊、色偏。

## 3. 指标

| 指标 | 定义 |
|---|---|
| 网格正确 | 列数和行数都完全正确 |
| **每千颗错误数（微平均，主指标）** | 数据集里所有错误格数之和 / 所有非空真值格数之和 × 1000。错误格包括：色号错误、把豆子识别成空格、把空格识别成豆子 |
| 非空格准确率（宏平均，辅助指标） | 每张图「非空格中识别正确的比例」，再对所有图取平均 |
| 空格误判 | 空格被识别成豆子的次数 + 豆子被识别成空格的次数，单独报告 |
| **零错误率** | 一格都没有错的图纸所占比例 |
| 用量清单误差 | Σ\|识别颗数 − 真值颗数\| / 总豆数 |
| 图例解析完全正确 | 色号集合和每个色号的颗数都完全正确 |
| **不确定标记** | 召回率 = 被标出的错误格 / 全部错误格；精确率 = 被标出的错误格 / 全部被标出的格；标记率 = 被标出的格 / 总豆数。**召回率必须在标记率不超过上限的前提下计算**（见 0.1 第 3 条），否则把所有格子都标为不确定就能刷出 100% 召回 |
| 失败 | 无法处理、程序崩溃，或网格尺寸错误（计分方式见 0.2） |
| 耗时、峰值内存 | 端侧实测 |

**汇总方式：**
- 按尺寸档、类型、难点标签分层报告；
- 用 bootstrap 估计 95% 置信区间；
- **和竞品比较时，在同一批图纸上做配对 bootstrap**：对每张图的错误格数差做重采样，比两组独立置信区间的统计功效高。

### 3.1 评测器的实现口径（T0.7，2026-10-28）

上面的定义有几处可以有不同读法，评测器（`bench/eval`）按下面的口径实现，完整的边界情况见 `bench/eval/README.md`：

1. **标记上限按每张图算**：每张图上限 = min(⌊2% × 该图豆数⌋, 30)，整个数据集的标记率自然 ≤ 2%。豆数少于 50 的图上限为 0。
2. **截断**：引擎标多了，按 confidence 从低到高保留到上限，并列时按格子编号。
3. **召回的分母**包含失败图的全部豆子（按 0.2「所有格子都按错误计算」）；另报一个不含失败图的召回作参考。没有错误格时召回无定义，门禁里按 1 处理。
4. **统计口径**：第 1、2、4 条、Hard/Clean 和门禁不含 T6、T7；第 3、6 条只排除 T7。
5. **失败图的用量清单误差**按 100% 计（等于没有输出）；最强竞品按这个口径选，报告附「不惩罚网格错误时最强竞品会不会变」的对照。
6. **图例完全正确**：预测多出任何一个色号就算错；同一色号多行时颗数相加。
7. **blurry**：「最小格边长」取每页每个方向的平均格距再取最小；拉普拉斯方差在真值网格线围成的矩形里算；人工标的 blurry 标签不参与 Hard 判定，只做对照。
8. **θ 的标定**：在 dev 集上按人工 blurry 标签取 Youden J 最大的阈值，并列取最小 θ（Clean 集更大，第 2 条更严）。**θ 未冻结时评测器拒绝运行 test 集。**
9. **最强竞品**：每个「App / 平台 / 导入路径」算一个独立条目，链接导入也参与排名（选出的竞品更强，判定更保守）。
10. **Tier B 缺文件**默认拒绝判定（否则结果会偏向 GO）；竞品处理失败要录成 error JSON。「≤ 50%」含等号。
11. **品牌**：真值 `palette_hint` 的品牌是主品牌，主品牌色号不带前缀；整张图纸认错品牌时每一格都算色号错误。
12. **尺寸档**一律由真值网格重新计算，不用手填的 `size_bucket`。

## 4. 竞品对比

### 4.1 对象

| 竞品 | 选择理由 | 获取方式 |
|---|---|---|
| 拼豆大王 | 用户口碑里识别最准 | 永久会员 ¥28–38 |
| AI 豆仓 | 用户量大 | 永久会员 ¥88 |
| 我嘞个豆 | 被推荐次数最多 | 免费（积分制） |
| 豆猫 | 高亮功能做得好 | 永久会员 ¥38.8 |
| 豆门 | 端侧 AI 识别，只有 iOS 版 | 免费 |
| 颂拼豆 | 完全免费 | 免费 |
| **LunarXuan/Pindo**（开源 baseline） | GPL-3.0。**只能作为外部进程运行**，不能复制进我们的代码。⚠️ 核实（2026-10-27）：它的识别功能只针对**不带色号**的图纸（README：Recognize unlabeled charts），而且是 Next.js 静态网页，没有命令行入口，要用无头浏览器驱动。对 T1（带色号）图纸它只能当颜色路径的 baseline，偏弱 | 本地运行（无头浏览器） |

会员费合计约 ¥200–300，由产品负责人购买。

### 4.2 测试协议

- **每个竞品走它自己最好的导入路径**：
  - 「导入图片」和「链接导入」都测，结果分开记录。
  - 我们自己不做链接导入（见 06 第 9 节），这一组的作用只是**量化链接导入带来的能力差距**。
- **固定版本**：记录竞品的 App 版本号和测试日期，每季度复测一次。
- **分三层（Tier）：**
  - **Tier A（全部 test 图纸）**：记录网格尺寸和用量清单，计算用量清单误差，并以此确定「最强竞品」。
  - **Tier B（test 集中的全部 Hard 图纸，约 40–50 张）**：做格子级对比。
    - 方法：导出竞品识别结果的 PNG 图纸 → 用我们自己的解析器读取这张干净的导出图 → 和真值逐格比较。
    - 解析器的正确性要先抽样验证，确认读取结果 100% 正确。
    - **第 0.1 节第 1 条只在 Tier B 上计算。**
  - **Tier C（20 张）**：请真实用户计时，测量「从导入到可以开始拼」需要多少人工修正时间。自研方案一起测。
- **自动化**：Android 端用 adb + uiautomator2 跑；iOS 端手动操作。
- **合规**：对外宣传时不点名竞品（《广告法》关于比较广告的规定）。

## 5. 端侧识别技术方案

### 5.1 Pipeline

```
输入：1 张或多张图片（RGBA，已在平台层完成解码和 EXIF 方向校正，见 03 §3.1）
  │
  ├─① 区域分割：图纸主体 / 图例 / 坐标条 / 标题 / 截图 UI
  │     T6（拍照）：先做透视校正
  │     T7（多图合集）：返回 needs_user_crop，交给 UI 让用户框选
  │
  ├─② 网格检测
  │     a. 投影轮廓找峰值 → 用自相关、comb 打分、run-length 多证据融合估计格距
  │        （参考 Retro-Diffusion/pixel-art-fixer，MIT）
  │     b. 逐条网格线局部精修（在预测位置附近找峰，再用单调样条或 DP 拟合），
  │        解决重采样带来的累积漂移
  │     c. 用每 5 / 10 格一条的粗线做结构锚点
  │     d. 识别四周的坐标数字，得到绝对索引和总格数，用来交叉验证
  │     e. 没有网格的像素画：估计像素尺寸
  │
  ├─③ 图例解析
  │     色块 + 色号 + 颗数
  │     → 色号的合法性校验：用「候选色卡的色号表」自动生成正则或词表，不写死
  │       （MARD 291 不只 A–M 系列）
  │     → 得到【封闭色板】（通常 10–40 色）和【期望颗数】
  │     → 根据色号集合判断品牌（功能 B8）
  │
  ├─④ 单格分类（多证据融合）
  │     颜色证据：取格子中心 50% 区域，剔除文字像素后取截尾中位数 → 转 Lab
  │               → 和【图例里渲染出来的色块颜色】算 ΔE2000 → 得到概率
  │     文字证据：格子 ≥ ~14 px 时，用小 CNN 在封闭词表上分类
  │     白豆 vs 空格：先看格内有没有文字；文字读不出来时，用图例颗数和「是否在轮廓内」辅助判断
  │     两种证据的 log 概率相加，再做温度校准
  │
  ├─⑤ 全局约束与纠错
  │     按图例颗数做约束：只调整低置信度的格子（min-cost 分配，规模小时可以用 ILP）
  │     邻域 MRF 平滑（保护单像素细节）
  │     置信度低于 τ 的格子标为不确定，同时保证标记率不超过上限
  │
  ├─⑥ 多页拼接：根据坐标标签对齐分页
  │
  └─输出：codebook、cells、置信度、不确定格列表、用量清单（格式见 03 §3.2）
```

**为什么用图例色块做匹配：**
- 每个 App 渲染同一个色号用的 HEX 不一样，公开色卡数据之间本身也有出入：pindou-color-data 收录的 MARD 221 两个来源中，有 77 个色号 HEX 不同。
- 图例色块和格子是同一个渲染器、同一轮压缩画出来的，颜色偏差一致，拿来匹配最稳。
- 候选范围从整套 291 色缩小到图例里的 10–40 色。

### 5.2 技术选型（以 03 和 05 为准）

| 层 | 选择 |
|---|---|
| 核心 | C++17 + OpenCV 4.x（只编译 core、imgproc 模块，**关闭 videoio、highgui**，避免引入 FFmpeg 和 GUI 依赖） |
| 推理 | ONNX Runtime（MIT），使用按算子裁剪的定制构建 |
| 色号分类 | 自训小 CNN（100–300 KB），用合成数据训练 |
| 图例和坐标文字识别 | 自训 CRNN + CTC，字符集由候选色卡的色号表生成。**App 里不用任何平台 OCR（Vision、ML Kit）**，保证 benchmark 的结果和线上 App 一致。PP-OCRv5/v6 只在训练和冷启动阶段用来做离线标注，**不打包进 App** |
| 网格和像素尺寸估计的参考 | pixel-art-fixer、proper-pixel-art、img2table（都是 MIT），只参考思路，自己重新实现 |
| 色卡数据 | 见 05 第 3 节（MARD 用 beadcolors 作为主数据源；国内其他品牌必须先核实数据来源） |

**端侧识别的意义：**
- 不上传图片，保护隐私；
- 边际成本为零，所以免费额度可以给得大方。

**性能预算：**
- 208×208 = 43,264 格，纯颜色路径目标 < 300 ms（桌面端）；
- CNN 只对文字可读的格子批量推理。

### 5.3 难例处理

| 难例 | 策略 |
|---|---|
| 水印覆盖 | 用图例色块做相对匹配 + 邻域先验 + 标为不确定 |
| 相近色（H1/H2 等） | 用图纸自身的图例色块匹配；判别余量小的格子标为不确定 |
| 白豆 vs 空格 | 看格内有没有文字 + 图例颗数约束 + 是否在轮廓内 |
| 极小格（≤ 6 px） | 只靠颜色判断；引导用户在小红书里「保存原图」，不要截图；分页大图要每一页都导入 |
| 拍照（T6） | 矩形检测 + 透视校正，先低通滤波再采样。首发版本标为实验功能 |
| 分页图（T4） | 按坐标标签拼接；没有坐标时让用户手动排序（免费功能 B9） |
| 多图合集（T7） | 让用户框选出单个图案 |
| 没有图例 | 退回到整套品牌色卡 + 自动判断品牌，整体置信度降一档 |
| 混用其他品牌的色号 | 以图例为准，codebook 支持一张图里出现多个品牌的色卡 |

## 7. 风险与待确认事项

1. **App 保存图的分辨率**：在 T0.3 里实测，它决定大图识别的输入上限。
2. **画师版权**：数据集只能内部使用。产品上要展示画师署名。
3. **竞品持续更新**：每季度复测一次。
4. **iOS 和 Android 差异**：评测时两端分开记录。
5. **统计功效**：Tier B 只有约 40–50 张图，如果配对比较的置信区间太宽、给不出显著结论，就把 test 集里的 Hard 图纸扩充到 ≥ 80 张之后再判定，**而不是降低门槛**。
